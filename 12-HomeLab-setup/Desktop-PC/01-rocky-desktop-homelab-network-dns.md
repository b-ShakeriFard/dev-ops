# Rocky Linux desktop: homelab network and DNS reference

This records the changes and checks performed on the Asus desktop running **Rocky Linux 8.10** on 26 September 2026. The Raspberry Pi Zero 2 W at `192.168.1.24` is the homelab DNS server. The Rocky desktop is a DNS **client**; its IP during this session was `192.168.1.11/24`.

| Item | Value observed |
| --- | --- |
| Rocky LAN interface | `enp4s0` |
| Rocky IP | `192.168.1.11/24`, supplied by DHCP |
| Router and default gateway | `192.168.1.1` |
| Ethernet NetworkManager profile | `Profile 1` |
| Desktop Ethernet MAC | `24:4b:fe:e0:38:0f` |
| Raspberry Pi DNS | `192.168.1.24` |
| Example local record | `dns.home.arpa → 192.168.1.24` |

## Check the desktop network

Run these on the **Rocky desktop**:

```bash
cat /etc/os-release
ip -br addr
ip route
cat /sys/class/net/enp4s0/address
nmcli -f NAME,DEVICE,TYPE connection show --active
```

`ip -br addr` is the correct short address command; `ip -br- addr` is a typo. Docker and libvirt add bridge interfaces, but `enp4s0` is the physical LAN connection. We identified `Profile 1` as its active NetworkManager profile.

To keep `.11` reliably, reserve `192.168.1.11` for MAC `24:4b:fe:e0:38:0f` in the router's **DHCP Static Leases** page. The desktop was receiving `.11` by DHCP; the screenshot did **not** establish that this reservation had been saved. Check the router before treating `.11` as guaranteed after a lease renewal or reboot.

## The directory-watch error

When restarting `NetworkManager` or `dnsmasq`, `systemctl` initially printed:

```text
Failed to allocate directory watch: Too many open files
```

The machine showed `fs.inotify.max_user_instances = 128`, `fs.inotify.max_user_watches = 241476`, and shell `ulimit -n = 1024`. The instance limit was raised temporarily and then persisted:

```bash
sudo sysctl -w fs.inotify.max_user_instances=1024
echo 'fs.inotify.max_user_instances=1024' | sudo tee /etc/sysctl.d/90-homelab-inotify.conf
```

Afterward, `systemctl status NetworkManager --no-pager` showed **active (running)** and subsequent service commands did not print the watch error. This is consistent with the inotify instance limit being the immediate problem, though we did not count instances per process. `nmcli` is a command-line utility, not a `nmcli.service`; the service name is `NetworkManager`.

Useful checks if the error returns:

```bash
sysctl fs.inotify.max_user_instances fs.inotify.max_user_watches
ulimit -n
sudo systemctl status NetworkManager --no-pager
```

## Why local DNS initially failed

The direct query to the Pi succeeded:

```bash
nslookup dns.home.arpa 192.168.1.24
```

But an ordinary `nslookup dns.home.arpa` returned `NXDOMAIN` because it went to an external DNS server such as `162.252.172.57`. We checked the NetworkManager profile and active interface:

```bash
nmcli -f ipv4.dns,ipv4.ignore-auto-dns,ipv6.ignore-auto-dns connection show 'Profile 1'
nmcli -f IP4.DNS,IP6.DNS device show enp4s0
ls -l /etc/resolv.conf
cat /etc/resolv.conf
```

NetworkManager already listed `192.168.1.24`, but `/etc/resolv.conf` said it had been generated by **`wg-quick` for WireGuard `wg0`** and listed external DNS servers. WireGuard's DNS override explained why the normal lookup bypassed the Pi.

## Set Rocky to use the Pi

On the Rocky desktop, we saved the Pi as the sole DNS server in the Ethernet profile, ignored DNS supplied by DHCP and IPv6, and reapplied the active interface:

```bash
sudo nmcli connection modify 'Profile 1' ipv4.ignore-auto-dns yes ipv4.dns '192.168.1.24' ipv6.ignore-auto-dns yes
sudo nmcli device reapply enp4s0
```

These profile settings persist in NetworkManager. They could not affect ordinary lookups while `wg-quick` still controlled `/etc/resolv.conf`.

## Remove the unwanted WireGuard connection

From the **local desktop terminal**, the `wg-quick@wg0` service was disabled and stopped, its interface was checked, its configuration file deleted, and the Ethernet profile reapplied:

```bash
sudo systemctl disable --now wg-quick@wg0
ip link show wg0
sudo rm -f /etc/wireguard/wg0.conf
sudo nmcli device reapply enp4s0
```

The check reported `Device "wg0" does not exist`. Deleting `wg0.conf` removed that connection's saved settings and private key. This did **not** establish that the `wireguard-tools` package was uninstalled; uninstalling the package was optional and was not shown in the final verification. We did not manually edit `/etc/resolv.conf`.

## Final verification

On Rocky, run:

```bash
nslookup dns.home.arpa
nslookup example.com
```

The final screenshot showed both queries using **`Server: 192.168.1.24`**. The first returned `192.168.1.24` for `dns.home.arpa`; the second returned public addresses for `example.com`. This verifies both the Pi's local record and external forwarding from this desktop at that time.

If a lookup fails in future, compare the default resolver with a direct Pi query:

```bash
cat /etc/resolv.conf
nmcli -f IP4.DNS,IP6.DNS device show enp4s0
nslookup dns.home.arpa 192.168.1.24
nslookup dns.home.arpa
```

The Pi's `dnsmasq` records are configured **on the Pi** in `/etc/dnsmasq.d/homelab.conf`; editing an identically named file on Rocky does not add records to the Pi. For a future `desktop.home.arpa → 192.168.1.11` record, first confirm the router's `.11` DHCP reservation, then add the record on the Pi, validate its configuration, restart its service, and query it from Rocky:

```ini
host-record=desktop.home.arpa,192.168.1.11
```

```bash
# Run on the Raspberry Pi after adding the line there:
sudo dnsmasq --test --conf-file=/etc/dnsmasq.d/homelab.conf
sudo systemctl restart dnsmasq

# Run on the Rocky desktop:
nslookup desktop.home.arpa
```

That desktop record and router reservation were **proposed next steps**, not verified as complete in the screenshots. Likewise, a reboot test of the desktop DNS setup has not yet been shown.
